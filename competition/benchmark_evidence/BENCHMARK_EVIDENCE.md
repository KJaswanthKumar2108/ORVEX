## 3. Energy Quadrature Accuracy & Gap Protection Verification

Energy estimation errors directly translate into inaccurate financial reports. ORVEX utilizes trapezoidal numerical quadrature bounded by a **30-second gap exclusion rule**.

$$\Delta E = \sum_{i=1}^{N} \frac{1}{2} \left[ P_{\text{excess}}(t_i) + P_{\text{excess}}(t_{i-1}) \right] \cdot \frac{t_i - t_{i-1}}{3600} \quad \text{for } (t_i - t_{i-1}) \le 30\text{ s}$$

### 3.2 The 30-Second Gap Exclusion Rule
If communication drops for 45 seconds, naive trapezoidal integration would assume power remained constant across the entire 45-second outage:
- **Naive Calculation:** $E = \frac{1}{2}(20\text{ kW} + 20\text{ kW}) \times \frac{45}{3600} = 0.250\text{ kWh}$ (phantom energy).
- **ORVEX Protection:** The condition $\Delta t = 45\text{s} > 30\text{s}$ triggers event boundary finalization. The interval $[t_{i-1}, t_i]$ is excluded from integration, and a new event is instantiated upon reconnect. Phantom energy generated = **0.000 kWh**.

## 7. Judge Differentiation Strategy

ORVEX stands apart from both generic cloud IoT dashboards and high-cost closed OEM SCADA systems.

### 7.1 Differentiator 1: Retrofit Compatibility with Legacy Equipment
- **What Makes It Distinctive:** Eliminates the need to replace multi-million dollar machinery. Compatible with any 3-phase induction motor (DOL, Star-Delta, Soft-Starter, or VFD).
- **How It Is Implemented:** Non-invasive split-core CTs clamped over existing cables inside the MCC bucket; voltage tapped via fused terminals; no mechanical coupling or shaft modifications required.
- **Evidence:** Tested on 5 distinct equipment types (Conveyors, Jaw Crushers, Dewatering Pumps, Ventilation Fans, Mine Hoists).
- **Remaining Limitations:** Requires physical space inside the MCC bucket for 3 split-core CTs and fused DIN-rail terminal blocks.

### 7.2 Differentiator 2: Affordable Sensing Architecture (< $350)
- **What Makes It Distinctive:** Complete edge sensing node Bill of Materials is **\$325.10 USD** (dropping to \$155.00 at scale), compared to \$5,000–\$15,000 for proprietary condition monitoring packages.
- **How It Is Implemented:** Certified DIN-rail Class 1.0 energy meter + MAX13487 isolated RS-485 transceiver + ESP32 microcontroller + DS18B20 1-Wire temperature sensor.
- **Evidence:** Documented itemized BOM with verified commercial supplier part numbers and invoices.
- **Remaining Limitations:** Current prototype uses an off-the-shelf carrier board rather than a unified production PCB.

### 7.3 Differentiator 3: Explainable Energy-Wastage Detection
- **What Makes It Distinctive:** Zero "black-box" machine learning. Operators receive clear mathematical justifications: *"Operated at 11.4% load with excess power of 15.1 kW for 180 seconds"*.
- **How It Is Implemented:** Calibrated piecewise linear power models ($P_{\text{expected}} = P_{\text{rated}} \cdot (\alpha_S + \beta_S \cdot L\%)$) combined with explicit operational state machines.
- **Evidence:** 100% precision and recall across 10 ground-truth validation scenarios; zero false alarms on inrush transients.
- **Remaining Limitations:** Piecewise parameters ($\alpha_S, \beta_S$) must be calibrated during initial machine commissioning.

### 7.4 Differentiator 4: Evidence-Backed Event Generation
- **What Makes It Distinctive:** Every alert is linked directly to a persisted `WastageEvent` record containing peak power, duration, timestamp boundaries, and numerical energy integral.
- **How It Is Implemented:** Foreign-key linkage between `alerts.event_id` and `wastage_events.id`, accessible via `/api/v1/wastage-events/{id}` and surfaced in the frontend Evidence Modal.
- **Evidence:** Verified live in Demonstration Center; operators can inspect raw electrical parameters that triggered the event.
- **Remaining Limitations:** Transient spikes below persistence thresholds (e.g., 55s idle when threshold is 60s) are logged in time-series telemetry but do not instantiate an event.

### 7.5 Differentiator 5: Honest Machine-Health Intelligence
- **What Makes It Distinctive:** Refuses to fake unmeasured channels. If an industrial vibration sensor is not physically connected, the system flags the parameter as `UNMEASURED_NOT_INSTALLED`.
- **How It Is Implemented:** Explicit guard `is_vibration_sensor_present` in `machine_health_service.py` prevents default "Healthy" assumptions or false vibration alerts.
- **Evidence:** Machine Health UI displays neutral dashed indicators for vibration while accurately evaluating real electrical unbalance and thermal limits.
- **Remaining Limitations:** Comprehensive mechanical diagnosis (bearing cage, outer race ball-pass frequencies) requires retrofitting high-bandwidth piezoelectric accelerometers.

### 7.6 Differentiator 6: Simulation-to-Physical Hardware Parity
- **What Makes It Distinctive:** The exact same backend ingestion pipeline, MQTT topics, database hypertables, and React frontend interact identically with physical ESP32 hardware and the multi-machine simulator.
- **How It Is Implemented:** Strict JSON schema adherence (`TelemetryCreateSchema`) across both the physical firmware Modbus publisher and the Python simulator service.
- **Evidence:** Stage 10A system integration audit demonstrated seamless switching between live ESP32 hardware and simulator scenarios without code changes.
- **Remaining Limitations:** Physical hardware currently communicates over 2.4 GHz Wi-Fi; harsh industrial underground mines require RS-485 Modbus TCP or Ethernet gateways.

### 7.7 Differentiator 7: Traceable Telemetry-to-Alert Workflow
- **What Makes It Distinctive:** Full operational lifecycle: Raw Telemetry $\to$ Feature Extraction $\to$ Wastage Event $\to$ Alert Notification $\to$ Operator Acknowledgment $\to$ Remediation Recommendation $\to$ Exportable Audit Report.
- **How It Is Implemented:** Complete relational model in TimescaleDB linking telemetry timestamps, events, alerts, and user resolution workflows, exportable via CSV.
- **Evidence:** End-to-end trace verified with 2.1 ms commit latency and full CSV report generation.
- **Remaining Limitations:** Currently does not integrate directly with third-party ERP/CMMS systems (e.g., SAP PM, IBM Maximo) via webhooks (planned for v2.0).
